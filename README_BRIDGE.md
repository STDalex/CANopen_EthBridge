# CAN–Ethernet Bridge API v1

Bridge — управляемый режим доступа к CANopen, а не прозрачный CAN↔Ethernet
туннель. В нём устройство принимает от одного Ethernet-клиента по одному
expedited SDO-запросу, передаёт его в CAN и возвращает результат. Одновременно
клиент получает полный поток кадров шины.

Обычная передача SDO с экрана и через `/api/v1/can/tx`, а также raw-передача
через `/api/v1/can/tx/raw`, на время Bridge блокируются. Монитор, список нод,
статистика и запись на microSD продолжают
работать.

## Жизненный цикл

1. `POST /api/v1/bridge/enable` включает режим и возвращает `session_id`.
2. Клиент подключается к
   `ws://<device>/api/v1/bridge?session_id=<session_id>`.
3. Клиент отправляет один SDO-запрос и ждёт `result` перед следующим.
4. `POST /api/v1/bridge/disable` завершает режим и принудительно возвращает CAN
   в SILENT.

`GET /api/v1/bridge/status` возвращает состояние, остаток lease, текущий запрос
и счётчики. Авторизация в v1 отсутствует; одновременно допускается один Bridge
клиент.

После включения или обрыва соединения действует lease 10 секунд. WebSocket
сервер раз в 2 секунды отправляет Ping; Pong или корректное сообщение клиента
продлевает lease. В течение lease клиент может подключиться повторно с тем же
`session_id`. После истечения lease Bridge выключается и CAN принудительно
переходит в SILENT.

## Команды WebSocket

Первое сообщение сервера — текстовый `hello`:

```json
{"type":"hello","protocol":1,"mode":"bridge","session_id":123,"lease_ms":10000,"sequence":456}
```

Expedited SDO-запрос передаётся текстовым JSON. `index`, `subindex` и `value`
являются JSON-числами; клиент может формировать их из привычной hex-записи.

```json
{"type":"sdo","request_id":1,"node_id":7,"command":"read","index":4096,"subindex":0,"timeout_ms":100}
```

Допустимые команды: `read`, `write_u8`, `write_u16`, `write_u24`, `write_u32`.
Для записи обязательно поле `value`. `timeout_ms` — 10…1000 мс.
`request_id` задаёт клиент, не равен нулю и используется для дедупликации.

Устройство сразу отвечает подтверждением:

```json
{"type":"ack","request_id":1,"tx_sequence":27,"status":"accepted"}
```

Возможные статусы: `accepted`, `duplicate`, `request_pending`,
`invalid_request`, `can_not_ready`, `bridge_disabled`, `not_connected`.
Для каждой Node ID мост держит не более одного ожидающего SDO-запроса. Новый
запрос к той же ноде получает `request_pending`; запросы к разным нодам могут
выполняться одновременно. После ответа следующая команда к этой ноде передаётся
сразу, без дополнительного интервала 50 мс.

WebSocket-кадр передаётся одной атомарной TCP-записью. Раздельная отправка его
заголовка и payload вызывала взаимодействие Nagle/delayed ACK и создавала
скрытую паузу около 40–50 мс на коротких сообщениях Bridge.

Готовый CAN-результат и входящие TCP-данные будят Bridge-задачу уведомлением
FreeRTOS. Успешные ответы выдаются событийно; прежний цикл опроса с
`vTaskDelay(2)` удалён. Таймер 10 мс используется только для обслуживания
timeout, lease и WebSocket ping при отсутствии событий.

После ответа или ошибки приходит итог:

```json
{"type":"result","request_id":1,"tx_sequence":27,"status":"completed","timestamp_us":1234567,"capture_time_us":1234567,"abort_code":0,"has_response":true,"can_id":1415,"dlc":8,"data":"4300100078563412"}
```

Итоги: `completed`, `abort`, `timeout`, `bus_off`, `driver_error`, `cancelled`,
`protocol_error`. При `abort` поле `abort_code` содержит 32-битный CANopen SDO
Abort code. Недавние итоги сохраняются в очереди и выдаются по порядку.
Прошивка не повторяет SDO автоматически: решение о повторе принимает клиент.
`capture_time_us` — непрерывная 64-битная метка от запуска устройства;
`timestamp_us` оставлено для совместимости с остальным REST API.

Сообщение `{"type":"ping"}` поддерживается как прикладной heartbeat и получает
ответ `{"type":"pong"}`; обычно достаточно стандартных WebSocket Ping/Pong.

## Поток CAN

Бинарные сообщения используют тот же формат `CSWS` v1, что
`/api/v1/stream`: 16-байтный заголовок и записи по 24 байта, little-endian.
Sequence относится ко всему потоку CAN. Кольцевая очередь ограничена 8192
кадрами; при отставании клиента заголовок сообщает точное `lost_count`.

Поле `flags` каждой записи:

| Бит | Значение |
|---:|---|
| 0 | extended CAN ID |
| 1 | RTR |
| 2 | локально переданный устройством кадр |
| 3 | SDO-запрос текущей Bridge-транзакции |
| 4 | SDO-ответ текущей Bridge-транзакции |
| 5 | кадр, не относящийся к текущему запросу клиента |

Так клиент одновременно видит собственную транзакцию и стороннюю активность
шины. Очередь ограничена, ожидание сети не блокирует CAN, анализатор или logger.

## Ограничения v1

- только Classic CAN и expedited CANopen SDO с predefined COB-ID;
- один Bridge-клиент и один незавершённый SDO-запрос;
- segmented/block SDO отмечается `protocol_error`;
- сервер не гарантирует доставку каждого фонового CAN-кадра медленному клиенту,
  но всегда сообщает sequence gap и число потерянных кадров;
- firmware 6.4.0 не содержит авторизации и шифрования, поэтому Bridge следует
  использовать только в доверенной диагностической сети.
