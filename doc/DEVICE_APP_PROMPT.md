# Промт для создания приложения через CanSniff Bridge

Скопируйте текст ниже в свою модель и приложите руководство, EDS или другой
документ со словарём объектов нужного CANopen-устройства. Замените текст в угловых
скобках на свои требования.

---

## Текст промта

Создай отдельное приложение для работы с CANopen-устройством через CanSniff
CAN–Ethernet Bridge API v1.

Исходные данные:

- задача: `<экраны, команды, телеметрия и поведение приложения>`;
- документ объектов/CANopen: `<путь, URL или вложение>`;
- Node ID или правило его выбора: `<значение>`;
- целевая ОС и формат: `<Windows EXE / Linux / web / другое>`;
- стек: `<имеющийся стек или "выбери сам">`;
- критерии готовности: `<проверяемые условия>`;
- каталог результата: `<путь или имя нового каталога>`.

Перед началом работы:

1. Прочитай целиком документ устройства, `README_BRIDGE.md` и `doc/CAN_BRIDGE_API.html`.
2. Составь таблицу используемых объектов: имя, `index:subindex`, access, wire type, размер,
   byte order, scaling, units, range, SDO/PDO и семантика abort/status.
3. Если постановки или документа нет, он нечитаем или в нём нет нужных индексов, не
   угадывай контракт: задай один короткий вопрос и останови реализацию.

Требования к архитектуре и протоколу:

1. Отдели сетевой транспорт, CANopen-кодек, модель состояния, планировщик опроса и UI.
   Сетевой I/O не должен блокировать UI.
2. Реализуй полный цикл Bridge v1: `GET /api/v1/bridge/status` → `POST /api/v1/bridge/enable` → WebSocket
   `/api/v1/bridge?session_id=...` → проверка `hello` → `ack` → `result` → heartbeat/lease →
   закрытие WebSocket и `POST /api/v1/bridge/disable`.
3. Не перехватывай чужую активную Bridge-сессию. После штатного Disconnect и закрытия окна
   гарантированно освобождай свою сессию.
4. Коррелируй `ack` и `result` по `request_id`; бинарные CSWS-пакеты могут приходить между ними.
5. Для каждой Node ID допускай не более одного незавершённого SDO. Запросы к разным нодам могут
   выполняться параллельно.
6. Для SDO-чтения проверяй COB-ID, DLC, command specifier, echo index/subindex, длину, wire type,
   byte order и abort code. Не интерпретируй payload только по длине.
7. Не повторяй запись автоматически после неопределённого сбоя. Сначала установи, была ли операция
   выполнена. Чтение можно повторить ограниченно после восстановления транспорта.
8. Запрашивай REST-диагностику отдельно, обычно около 1 Гц. Таймаут REST не равен обрыву основного
   WebSocket.
9. Отдельно показывай CAN controller errors, SDO abort/timeout/rejected, потери CSWS sequence,
   ring/GUI drop и свежесть данных.
10. Не добавляй операции записи в объекты, не помеченные в документе как RW/WO. Не добавляй
    функции microSD, скачивания `.CSL` или сравнения логов, если этого нет в постановке.

Проверка и результат:

1. Добавь unit-тесты кодеков, scaling, limits и модели состояния.
2. Протестируй эмуляцию `hello → ack → result`, бинарные пакеты между ними, abort, timeout,
   обрыв, lease и освобождение сессии.
3. Проведи аппаратную пробу только если CanSniff и CAN-устройство доступны и такая проба разрешена.
4. Собери поставляемый артефакт и кратко опиши: прочитанные источники, реализованный контракт,
   проверки, путь к артефакту и оставшиеся аппаратные допущения.
