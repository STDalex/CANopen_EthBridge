CAN–Ethernet Bridge · protocol v1

Управляемый доступ к CANopen через Ethernet

API для диагностических клиентов, которым нужны транзакции expedited SDO и непрерывный поток всех кадров CAN. Bridge управляет режимом передачи и безопасно возвращает устройство в SILENT при завершении сессии.

01 · Назначение

Не прозрачный туннель, а диспетчер SDO-транзакций

Клиент не отправляет произвольные CAN-кадры. Он описывает операцию CANopen, а прошивка формирует стандартный COB-ID, контролирует передачу, сопоставляет ответ и возвращает итог.

SDO

Чтение и запись объектов

Поддерживаются expedited read и write на 8, 16, 24 или 32 бита для Node ID 1…127.

CSWS

Параллельный CAN-поток

В том же WebSocket приходят бинарные пакеты со всеми кадрами, метками времени и признаками Bridge-транзакций.

10 s

Fail-safe lease

Если heartbeat исчезает, Bridge отменяет ожидания, освобождает TX и принудительно переводит CAN в SILENT.

02 · Общая логика

Жизненный цикл соединения

REST управляет сессией. WebSocket переносит команды, результаты и поток CAN. Клиент должен хранить session_id и уникальные ненулевые request_id.

Проверить

GET /status. Если active=true и connected=true, Bridge уже занят.

Включить

POST /enable резервирует CAN TX и возвращает session_id. CAN должен быть синхронизирован.

Подключить WS

Открыть /bridge?session_id=…, дождаться hello, затем отправлять SDO-команды.

Завершить

Закрыть WebSocket и вызвать POST /disable. При аварии это сделает lease по истечении 10 секунд.

Повторное подключение.

После сетевого обрыва тот же session_id можно использовать до истечения lease, если прежний WebSocket уже освобождён.

Bridge — эксклюзивный владелец TX.

Пока он активен, изменение CAN-конфигурации и режима, локальные SDO и /api/v1/can/tx блокируются. Мониторинг и logger продолжают работать.

03 · WebSocket

Текстовые события + бинарный поток

Текстовые сообщения — UTF-8 JSON. Клиентские WebSocket-кадры должны быть masked и не фрагментированы; текстовый payload ограничен 512 байтами.

04 · Quick start

Минимальная интеграция

JSON использует десятичные числа: например, индекс 0x6008 передаётся как 24584. Hex нужен только для поля result.data.

$base = 'http://192.168.1.7'

# 1. Проверить состояние
Invoke-RestMethod -Method Get `
  -Uri "$base/api/v1/bridge/status"

# 2. Включить Bridge и получить session_id
$session = Invoke-RestMethod -Method Post `
  -Uri "$base/api/v1/bridge/enable" `
  -ContentType 'application/json' `
  -Body '{}'
$session.session_id

# 3. В конце обязательно выключить Bridge
Invoke-RestMethod -Method Post `
  -Uri "$base/api/v1/bridge/disable" `
  -ContentType 'application/json' `
  -Body '{}'

# Альтернатива: настоящий curl, обязательно с суффиксом .exe
curl.exe -X GET "$base/api/v1/bridge/status" -H "accept: */*"
BASE=http://192.168.1.7

# 1. Получить session_id
curl -sS -X POST "$BASE/api/v1/bridge/enable" \
  -H "Content-Type: application/json" -d '{}'

# 2. Проверять состояние
curl -sS "$BASE/api/v1/bridge/status"

# 3. В конце обязательно выключить Bridge
curl -sS -X POST "$BASE/api/v1/bridge/disable" \
  -H "Content-Type: application/json" -d '{}'
const sessionId = 123; // из POST /enable
const ws = new WebSocket(
  `ws://192.168.1.7/api/v1/bridge?session_id=${sessionId}`
);
ws.binaryType = "arraybuffer";

ws.onmessage = ({ data }) => {
  if (typeof data !== "string") return parseCsws(data);
  const message = JSON.parse(data);
  if (message.type === "hello") {
    ws.send(JSON.stringify({
      type: "sdo", request_id: 1, node_id: 7,
      command: "read", index: 0x6008,
      subindex: 0, timeout_ms: 150
    }));
  }
  if (message.type === "ack" && message.status !== "accepted" &&
      message.status !== "duplicate") {
    console.error("SDO rejected", message);
  }
  if (message.type === "result") console.log(message);
};
import struct

HEADER = struct.Struct("<4sBBHII")
FRAME = struct.Struct("<QIBB2x8s")

def parse_csws(payload: bytes):
    magic, version, flags, count, sequence, lost = HEADER.unpack_from(payload)
    if magic != b"CSWS" or version != 1:
        raise ValueError("unsupported CSWS packet")
    if len(payload) != HEADER.size + count * FRAME.size:
        raise ValueError("invalid CSWS size")
    for offset in range(HEADER.size, len(payload), FRAME.size):
        timestamp_us, can_id, frame_flags, dlc, data = FRAME.unpack_from(payload, offset)
        yield timestamp_us, can_id, frame_flags, data[:dlc]
    return sequence, lost
05 · Надёжность

Не продолжайте обмен через повреждённый WebSocket

CAN-ответ может быть успешно принят прошивкой, даже если соответствующий result не дошёл до клиента из-за временной сетевой паузы или разрыва TCP. Клиент должен отличать CAN timeout от ошибки транспорта и уметь восстановить сессию.

Профилактика

Освобождайте короткие сообщения сразу

Для нативного TCP-клиента включите TCP_NODELAY до WebSocket handshake. Это не позволяет Nagle задержать короткий sdo, ack или result до delayed ACK. Браузерный WebSocket не предоставляет эту настройку; в браузере её контролирует сетевой стек.

Чтение потока

Один непрерывный receive-loop

Постоянно разбирайте все входящие кадры: текстовые ack/result, бинарные CSWS, ping и close. Если не вычитывать бинарный поток, TCP receive window заполнится и нужный result окажется за накопившимися данными.

Тайм-ауты

ack не завершает SDO

После accepted ждите result с тем же request_id. Сетевой deadline должен быть больше переданного timeout_ms; практический запас — не менее 1 секунды. Socket timeout, EOF, invalid frame и отсутствие result являются ошибками транспорта, а не CAN timeout.

Восстановление

Закрыть, переподключить, повторить

После транспортной ошибки прекратите новые SDO через старый сокет. Закройте WebSocket, дождитесь освобождения подключения и присоединитесь с тем же session_id до окончания lease либо выполните управляемый цикл /disable → /enable → hello. Затем повторите незавершённое чтение.

Как распознать именно сетевой сбой.

Если клиент не получил result, но GET /api/v1/bridge/status показывает рост completed при timeouts=0, инклинометр ответил и результат был сформирован: потерян транспорт до клиента. Не выполняйте ещё несколько циклов через тот же сокет — сразу пересоздайте WebSocket.

Рекомендуемый алгоритм клиента

# Для нативного клиента, до WebSocket handshake:
socket.setsockopt(IPPROTO_TCP, TCP_NODELAY, 1)

try:
    send_sdo(request_id)
    wait_ack(request_id)
    result = wait_result(request_id, can_timeout + 1.0)
except (SocketTimeout, ConnectionClosed, InvalidWebSocketFrame):
    stop_sending_on_old_socket()
    close_websocket()
    reconnect_bridge_and_wait_hello()
    result = retry_read(request_id)

# При восстановлении той же сессии повторяйте тот же request_id:
# Bridge распознает duplicate и вернёт сохранённый результат, если он ещё
# находится среди последних 32 итогов.
Осторожно с повтором записи.

SDO read можно безопасно повторить. Для write после полного /disable → /enable исход предыдущей операции может быть неизвестен: сначала прочитайте объект и проверьте значение. Автоматически повторять abort, настоящий CAN timeout или driver_error без анализа причины не следует.

06 · Ограничения

Что должен учитывать клиент

Ограничения ниже относятся к протоколу v1 и текущей реализации прошивки.

01

Только Classic CAN. CAN FD не поддерживается; DLC результата и потока не превышает 8.

02

Только expedited SDO. Segmented и block transfer завершаются protocol_error.

03

Predefined COB-ID. Запросы идут на 0x600 + node_id, ответы ожидаются на 0x580 + node_id.

04

Один WebSocket-клиент. Второе подключение получает HTTP 409 bridge_unavailable.

05

Один pending на Node ID. Разные ноды можно опрашивать параллельно; повтор к занятой ноде получает request_pending.

06

TX-очередь 16 записей. При перегрузке подтверждение получает can_not_ready; клиент выбирает стратегию retry.

07

Результаты хранятся ограниченно. Последние 32 итога нужны для дедупликации; request_id следует увеличивать и не переиспользовать.

08

Поток lossy. Кольцо — 8192 кадра. Медленный клиент получает sequence gap и точный lost_count, но не вытесненные данные.

09

Timeout 10…1000 мс. По умолчанию 100 мс; отсчёт начинается после фактической передачи CAN-запроса.

10

Нет автоматических повторов. После timeout, abort или driver error решение о retry принимает клиент.

11

Нет auth и TLS. Любой узел сети может включить или выключить Bridge и получить session_id. Использовать только в изолированной доверенной сети.

12

Swagger не является WS-клиентом. Он выполняет REST-запросы и показывает контракт; для WebSocket используйте приложение или библиотеку RFC 6455.

CORS.

Прошивка не добавляет CORS-заголовки. Кнопка Try it out в Swagger работает, когда документация обслуживается с того же origin, что и API, либо когда запрос выполняется не из браузера. Для локальной диагностики надёжнее использовать curl, Python или Postman.

В Windows PowerShell команда curl может быть псевдонимом Invoke-WebRequest, поэтому параметры -X/-H и перенос строки через \ завершаются ошибкой. Используйте нативную команду:

Invoke-RestMethod -Method Get -Uri 'http://192.168.1.7/api/v1/bridge/status'
