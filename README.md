# CANopen Ethernet Bridge для STM32F746G-DISCO

Прошивка превращает отладочную плату STM32F746G-DISCO в автономный
CAN/CANopen-анализатор, регистратор и управляемый CAN–Ethernet Bridge. Устройство
показывает состояние шины на встроенном дисплее, сохраняет трафик на microSD и
предоставляет REST/WebSocket API для внешних приложений диагностики.

Актуальная версия: [v6.5.0](https://github.com/STDalex/CANopen_EthBridge/releases/tag/v6.5.0).

Проект рассчитан на Classic CAN и CANopen. По умолчанию контроллер работает в
безопасном режиме `silent`: принимает кадры, но не передаёт данные и не формирует
ACK. Активная передача включается только явно.

## Основные возможности

- автоматическое определение скорости CAN: 10, 20, 50, 100, 125, 250, 500,
  800 и 1000 кбит/с;
- мониторинг Classic CAN с временными метками и оценкой загрузки шины;
- анализ CANopen-узлов, NMT, PDO, EMCY и expedited SDO;
- отправка адресных и broadcast-команд CANopen NMT через REST API, а также
  управление каждой обнаруженной нодой из Web-интерфейса;
- чтение и запись expedited SDO через экран и REST API;
- двунаправленный raw Classic CAN: входящие STD/EXT и DATA/RTR кадры доступны
  в WebSocket-потоке, произвольные исходящие кадры отправляются через REST API
  и вкладку `Передача → Raw CAN` в Web-интерфейсе;
- поток CAN-кадров через WebSocket для четырёх независимых слушателей;
- управляемый CAN–Ethernet Bridge с одной клиентской сессией;
- запись полного или отфильтрованного трафика на microSD;
- сенсорный интерфейс на дисплее STM32F746G-DISCO;
- настройка Ethernet, CAN и регистратора через REST API;
- две системы сборки: Keil MDK-ARM и CMake с GNU Arm Embedded Toolchain.

Подробное описание Bridge-протокола находится в
[README_BRIDGE.md](README_BRIDGE.md), интерактивная документация API — в
[doc/CAN_BRIDGE_API.html](doc/CAN_BRIDGE_API.html). Готовый промт для создания
собственного приложения к CANopen-устройству — в
[doc/DEVICE_APP_PROMPT.md](doc/DEVICE_APP_PROMPT.md).

## Подключение CAN-трансивера к STM32F746G-DISCO

На STM32F746G-DISCO нет встроенного CAN-трансивера. Логические сигналы CAN1
выведены на Arduino-разъём CN7. Между платой и линиями `CAN_H`/`CAN_L`
необходима внешняя микросхема физического уровня CAN. Выбирайте трансивер,
совместимый с логическими уровнями 3,3 В на `TXD` и `RXD`.

| STM32F746G-DISCO | CAN-трансивер | Назначение |
|---|---|---|
| CN7 pin 9, D14, PB9, CAN1_TX | TXD / DI | Передача от STM32 к трансиверу |
| CN7 pin 10, D15, PB8, CAN1_RX | RXD / RO | Приём от трансивера в STM32 |
| CN6 pin 4, 3V3 | VCC/VIO 3,3 В | Питание 3,3-вольтового трансивера или его логической части |
| CN6 pin 5, 5V | VCC 5 В | Питание 5-вольтового трансивера |
| CN6 pin 6 или 7, GND | GND | Общая земля |

Используйте только то напряжение питания, которое требует выбранная микросхема;
выводы standby/enable подключаются по её datasheet. `CAN_H` и `CAN_L` идут на шину через
трансивер и не подключаются напрямую к STM32. Терминация шины выполняется по общим правилам CAN.

Минимальная схема сигналов:

```text
STM32F746G-DISCO             CAN-трансивер             CAN-шина

CN7.9  D14 / PB9 / CAN1_TX  ---> TXD
CN7.10 D15 / PB8 / CAN1_RX  <--- RXD
CN6.4  3V3 или CN6.5 5V  ---> VCC/VIO
CN6.6/7 GND                 --- GND
                                  CANH --------------- CAN_H
                                  CANL --------------- CAN_L
```

Для пассивного мониторинга достаточно режима `silent`, но такой узел не
формирует ACK. Если передатчик один на шине, для нормального обмена и проверки
CANopen следует включить active mode либо подключить другой активный CAN-узел.

## Сборка GNU Arm через CMake

CMake-сборка использует те же исходники, что и проект Keil, и создаёт прошивку
для STM32F746NGHx с аппаратным FPU. Linker script сохраняет размещение специальных
буферов SD, Ethernet и внешней SDRAM.

### Требования

- CMake 3.22 или новее;
- Ninja;
- GNU Arm Embedded Toolchain (`arm-none-eabi-gcc`);
- STM32CubeProgrammer для прошивки через ST-Link.

На Windows toolchain-файл автоматически ищет GNU Arm и Ninja из установленной
STM32CubeIDE. Для отдельной toolchain можно явно задать каталог `bin`:

```powershell
$env:ARM_GCC_PATH = 'C:\path\to\arm-gnu-toolchain\bin'
```

### Конфигурация и сборка Release

Команды для Windows PowerShell:

```powershell
cmake -S . -B build/gcc-release -G Ninja `
  -DCMAKE_TOOLCHAIN_FILE=cmake/arm-none-eabi-gcc.cmake `
  -DCMAKE_BUILD_TYPE=Release

cmake --build build/gcc-release --parallel
```

Результаты находятся в `build/gcc-release`:

- `CAN_sniffer.elf` — ELF с отладочными символами;
- `CAN_sniffer.hex` — образ для программатора;
- `CAN_sniffer.bin` — бинарный образ от адреса `0x08000000`;
- `CAN_sniffer.map` — карта памяти.

### Прошивка через ST-Link

Подключите разъём ST-LINK USB на STM32F746G-DISCO и выполните:

```powershell
cmake --build build/gcc-release --target flash
```

Цель `flash` использует STM32CubeProgrammer, записывает HEX, проверяет содержимое
Flash и перезапускает микроконтроллер.

Дополнительные пояснения приведены в [BUILD_CMAKE.md](BUILD_CMAKE.md). Проект
Keil сохранён в каталоге `MDK-ARM` и может использоваться параллельно.

## Первый запуск

1. Подключите CAN-трансивер и проверьте общую землю и терминацию CAN.
2. Подключите Ethernet и питание/ST-Link USB.
3. Соберите и прошейте проект.
4. Узнайте адрес устройства по DHCP или задайте статический адрес на экране.
5. Откройте `http://<IP-адрес>/` либо проверьте API:

```powershell
curl.exe http://<IP-адрес>/api/v1/state
```

В PowerShell следует запускать именно `curl.exe`: команда `curl` в старых
версиях Windows PowerShell может быть псевдонимом `Invoke-WebRequest`.

## Чтение логов и выбор microSD

В каталоге [log_analyzer](log_analyzer) находится графическая утилита для Windows и её
исходники на Python. Она открывает карту или отдельный файл `.CSL`, проверяет CRC,
показывает кадры и статистику CAN/CANopen, фильтрует запись и экспортирует выборку в CSV.
Для запуска без Python используйте `log_analyzer/CanSniff_Log_Analyzer.exe`.

Для регистратора рекомендуется качественная microSDHC 8…32 ГБ класса Class 10/U1,
лучше серии High Endurance или Industrial. Карту следует отформатировать в FAT32;
exFAT в текущей сборке FatFs отключён. Для длительной записи не стоит использовать безымянные
или сомнительные карты.

## Создание собственного приложения

Шаблон [DEVICE_APP_PROMPT.md](doc/DEVICE_APP_PROMPT.md) можно передать любой модели вместе с
руководством или словарём объектов нужного CANopen-устройства. Заполните в начале
промта постановку задачи, путь к документу, целевую ОС/формат и критерии готовности. Шаблон
требует опираться на документ, корректно освобождать Bridge-сессию и покрывать протокол тестами.

## Raw CAN через REST API

`POST /api/v1/can/tx/raw` ставит произвольный Classic CAN-кадр в ту же
ограниченную очередь передачи, что и SDO/NMT. Поддерживаются стандартные и
расширенные ID, DATA и RTR, DLC 0…8, разовая и периодическая передача. Пример:

```json
{
  "can_id": 291,
  "extended": false,
  "remote": false,
  "dlc": 4,
  "data": "11 22 33 44",
  "timeout_ms": 100
}
```

Для периодической передачи добавьте `"period_ms": 1000`. Число байт `data`
должно совпадать с DLC; RTR-кадр передаётся с пустым `data`. Raw-передача
недоступна, пока активна эксклюзивная Bridge-сессия. Встроенный сенсорный экран
остался CANopen-ориентированным и не содержит формы отправки raw-кадров.

## Ограничения

- поддерживается Classic CAN, но не CAN FD;
- live WebSocket-поток поддерживает максимум четыре одновременных слушателя;
- Bridge v1 обслуживает одного WebSocket-клиента;
- Bridge v1 принимает команды expedited SDO; произвольная raw-передача
  выполняется отдельным REST endpoint вне Bridge-сессии;
- segmented и block SDO не поддерживаются;
- в API v1 нет авторизации и TLS, поэтому устройство следует использовать
  только в доверенной локальной сети.
