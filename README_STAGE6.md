# CAN sniffer — этап 6, задачи 1–3: безопасная активная передача

## Безопасное переключение режима

После reset устройство всегда стартует в `CAN_MODE_SILENT`. PB9 (CAN TX) при
этом программно отсоединён от alternate function bxCAN, настроен как обычный
выход и удерживает TXD трансивера в рецессивном состоянии. Этот GPIO-gate не
зависит от программного silent mode контроллера и открывается только после
успешного перехода bxCAN в normal mode.

Для разового запроса менеджер сам кратковременно переводит контроллер в normal
mode, оставляет его активным на время ожидания SDO-ответа и автоматически
возвращает в silent mode. Периодический запрос удерживает передачу активной до
явной остановки и помечается фиолетовым. Изменение bitrate, bus-off или ошибка
переключения закрывают TX gate, останавливают периодический запрос и возвращают
устройство в silent mode.

Для штатного приёма PI2 / S трансивера остаётся в нуле. Независимый аппаратный
запрет передачи реализован именно переключением PB9 между GPIO-high и AF9,
поскольку на фактически установленном модуле S=1 одновременно нарушает приём.

## TX manager

Только `can_tx_manager.c` вызывает `HAL_CAN_AddTxMessage`; другие задачи
помещают проверенный запрос в статическую очередь. Ограничения:

- очередь: 16 кадров;
- rate limit: не более 20 попыток передачи в секунду;
- timeout одного кадра: 10–1000 мс, по умолчанию 100 мс;
- наружу принимаются только expedited CANopen SDO client-запросы: чтение и
  запись беззнаковых значений размером 8, 16, 24 или 32 бита;
- CAN ID формируется как `0x600 + Node ID`, кадр всегда Standard Data с DLC 8;
- auto retransmission отключён, поэтому arbitration lost фиксируется как
  отдельный результат, а не скрывается бесконечными повторами;
- журнал в RAM: 32 последних результата (`sent`, `cancelled`, `timeout`,
  `arbitration_lost`, `bus_off`, `driver_error`, `mode_disabled`).

Локальный экран позволяет ввести Node ID, индекс объекта, субиндекс и значение,
выбрать чтение или размер записи, отправить разовый SDO-запрос или запустить
его периодическую отправку. Node ID и период вводятся через цифровую клавиатуру LVGL,
а объект, субиндекс и значение — через компактную HEX-раскладку.

## REST API

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/api/v1/can/mode` | режим, TX gate, bitrate и причина safe fallback |
| POST | `/api/v1/can/mode` | переход в `active` или `silent` |
| GET | `/api/v1/can/tx` | глубина очереди и счётчики результатов |
| POST | `/api/v1/can/tx` | проверка и постановка SDO-запроса в очередь |
| DELETE | `/api/v1/can/tx/periodic` | остановка периодического SDO-запроса |
| POST | `/api/v1/can/tx/{sequence}/cancel` | отмена ожидающего/текущего запроса |
| GET | `/api/v1/can/tx/history` | 32 последних результата |

Пример чтения объекта `0x1018:01` у ноды 1:

```json
{
  "node_id": 1,
  "command": "read",
  "index": 4120,
  "subindex": 1,
  "value": 0,
  "timeout_ms": 100
}
```

Если добавить `"period_ms": 1000`, запрос запускается периодически. Допустимый
период — 50…3 600 000 мс и не короче `timeout_ms`. В TX-журнале периодический
запрос занимает одну строку: обновляются время, последний результат и счётчик
попыток.

Для записи поле `command` принимает `write_u8`, `write_u16`, `write_u24` или
`write_u32`, а `value` должно помещаться в выбранный размер. Успешная постановка
отвечает `202 Accepted` и возвращает `sequence`. Произвольные CAN Data/Remote
кадры через экран и REST API не принимаются.

Токены, allowlist, сохранённые запросы и CAN–Ethernet gateway относятся к
следующим задачам этапа и в этой части не включены.
